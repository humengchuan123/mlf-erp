# 《水镜零售 ERP 系统全面审计与后续开发建议》评审与 mlf-erp 对照

> **评审日期：** 2026-11-25
> **输入报告：** `docs/reports/2026-11-25-shuijing-retail-erp-audit.md`（外部审计，报告日期 2026-08-03）
> **对照对象：** `mlf-erp`（Go + Gin + PostgreSQL + Vue 3）
> **方法：** 按业务能力映射，不按报告的表名、端点或文件名逐字匹配；证据来自当前仓库代码、迁移、OpenAPI、测试和页面。
> **结论：** 报告可作为 ERP 领域问题清单和需求假设，但不能作为 `mlf-erp` 的可复现审计证据。报告 P0 中的总账、自动凭证、期末结转和多币种汇兑在 `mlf-erp` 已完成；真正需要优先投入的是资金操作幂等/审批、成本核算收口、库存作业、权限精细化，以及报告遗漏的安全、可观测性和灾备。

## 1. 执行摘要

### 1.1 报告优点

- 结构清晰：现状 → 功能清单 → 表 → API → 页面 → 问题 → 建议，便于快速定位。
- 领域拆分合理：`sys / md / sd / pd / inv / fin / rpt` 与单据链条（报价→订单→发货→退货；申请→订单→收货→退货）可作为 ERP 能力检查表。
- 问题主题抓得准：总账勾稽、成本核算、汇兑、期末结转、反核销/红冲、审批流、批次/序列号，都是贸易/分销 ERP 的核心风险。
- 归档时已明确标注技术栈与当前仓库不同，避免了直接把报告当成 `mlf-erp` 现状。

### 1.2 报告关键问题

- **没有方法与证据**：没有代码版本、环境、数据规模、工具、访谈记录或限制说明；没有文件、SQL、配置、日志、查询计划或测试引用；没有区分“观察到的缺陷”“推断”和“假设”。
- **财务核心自相矛盾**：§1.3/§2.6/§2.7 声称已有凭证、科目、期间、三大报表和毛利报表；§6.1 又说缺少完整复式记账总账、成本核算和期末结转。报告没有定义“凭证录入”“总账”“结账”“期末结转”的区别。
- **产品范围未定义**：标题是“零售”，结论是“贸易/分销”，功能清单没有 POS、门店补货、促销、会员、条码、保质期等零售能力；也没有行业、规模、部署形态、合规要求，导致 P0/P1 无法审计。
- **安全与多租户缺失**：只把权限粒度作为问题，没有威胁模型、JWT/会话生命周期、密钥管理、注入/XSS/CSRF、限流/锁定、MFA、加密、依赖扫描、审计日志完整性或多租户隔离评估。
- **P0 不可执行且重复规划**：把完整总账、自动凭证、应收应付勾稽、期末结转、成本核算、汇兑损益、外币折算和汇率维护放进 1–2 个月，没有团队规模、工作量、依赖、迁移或验收标准；同时重复要求“汇率维护”“库存预警”等报告已声称存在的功能。

### 1.3 对 mlf-erp 的核心结论

- **不要重做已完成的财务核心**：总账、自动凭证、期末/年度结转、税务发票、多币种汇兑与重估、现金流量表、销售/采购退货、贷项抵用/退款、收付款反核销均已落地，并有 Stage 3B–3K 接口测试。
- **成本核算不是“从零建设”**：已有库存移动平均成本、发货 COGS、退货回库重算和 COGS 凭证；缺的是成本调整、月结成本、成本报表、负库存策略和与总账的正式对账。
- **真正的高优先级差距**：
  1. 资金操作幂等与审批/职责分离（退款、收付款、反核销、发货、收货、退货）。
  2. 成本核算收口与存货-总账对账。
  3. 库存作业（调拨、盘点、预留、预警）与批次/序列号/保质期。
  4. 权限精细化（字段级、数据范围管理 UI、权限实时刷新）。
  5. 报表中心（销售/采购/库存/账龄/对账）与导出。
- **报告遗漏但必须补的工程项**：幂等/并发、安全加固、多租户 RLS、可观测性、备份/灾备、迁移/切换、合规与用户手册。
- **前端/契约也有明确差距**：无 `el-form` 规则校验（手工 `if` + toast）、无 404 路由、无改密/个人资料页、Dashboard 为静态占位、无 i18n/列配置/E2E；OpenAPI 缺 12 个 system path（约 19–20 个 operation），`masterdata` enable 路径与后端不一致，`check-frontend` 只做字符串存在性检查。

## 2. 报告质量评审

### 2.1 优点

- **结构可导航**：编号章节 + 表格 + 清单，读者可以快速跳到关心的模块。
- **清单可复用**：系统/主数据/销售/采购/库存/财务/报表的拆分，以及头表/行表成对、单据链条，适合作为 ERP 需求检查表。
- **主题选择正确**：§6.1–§6.4 覆盖了 ERP 最常见的财务与流程风险。
- **来源透明**：归档说明标注了报告日期、原始技术栈和与当前仓库的差异。

### 2.2 关键问题

#### Critical

1. **没有可复现的方法与证据。**
   - 没有代码 revision、环境、数据集、工具、访谈或限制说明；没有文件、类、SQL、配置、日志、查询计划或测试引用。
   - 没有标注“观察到 / 推断 / 假设”；唯一量化是“约 150 个 Python 文件、约 80 个 Vue 文件、60+ 张表、100+ 个 API”。
   - 报告日期 2026-08-03、归档日期 2026-11-25，代码可能已变化；没有 revision 就无法复现。

2. **财务核心自相矛盾。**
   - §1.3 说阶段六“财务基础”已完成；§2.6 列出凭证录入/审核/查询/打印、科目、期间结账/反结账；§2.7 列出资产负债表、利润表、现金流量表、销售毛利。
   - §6.1 又说“缺少完整的复式记账总账体系”“缺少成本核算”“缺少期末结转”“应收应付与总账勾稽不完整”。
   - 部分表述可以调和（凭证录入 ≠ 总账；期间锁定 ≠ 期末结转；子账账龄 ≠ 总账勾稽），但报告没有定义术语；直接冲突是“已有三大报表/毛利”与“没有总账/COGS”，以及“已用移动加权平均”与 P0“实现移动加权平均”。

3. **产品范围未定义。**
   - 标题“零售”与结论“贸易/分销”冲突；功能清单没有零售特有能力的描述。
   - 没有行业、企业规模、用户数、交易量、单租户/SaaS、合规要求；这些直接决定批次/序列号、审批流、字段级权限、外币折算的优先级。

4. **安全与租户隔离没有评估。**
   - 权限只覆盖 RBAC 粒度；没有认证/会话/JWT 生命周期、密钥管理、注入/XSS/CSRF、限流/锁定、MFA、加密、依赖/供应链扫描、审计日志完整性或渗透测试。
   - 多租户完全缺失；组织树不等于租户隔离。对于持有财务数据的 ERP，这是关键缺口。

5. **P0 不可执行且重复规划。**
   - 1–2 个月完成完整总账、自动凭证、勾稽、期末结转、成本核算、汇兑、外币折算和汇率维护，没有团队规模、工作量、依赖、迁移或验收标准；对小团队更像多季度财务项目。
   - 重复要求“汇率维护”（§2.2 已声称有）和“库存预警”（§2.5/§4.6/§5.5 已声称有）。
   - 字段级权限和报表/图表被过度优先；安全、幂等、测试、迁移/灾备、可观测性和税务合规被低估。

#### Important

6. **功能、表、API、页面清单不对账。**
   - 价格管理（§2.3、`/sales/prices`）没有价格表（§3.3）和端点（§4.4）。
   - 客户/供应商导入导出没有对应端点。
   - 系统配置有页面和表，但没有 API。
   - 权限管理只有 `GET /api/system/permissions`，没有 CRUD。
   - 字典项没有 item 级端点。
   - 物料分类、单位换算、汇率维护没有 API/页面。
   - 库存预警没有阈值表/字段。
   - `rpt_*` 报表表没有物化/刷新说明。

7. **发现项不可验证。**
   - “部分列表存在 N+1”“缺少索引优化”“单元测试覆盖率低”“部分表单缺少前端校验”都没有端点、数量、查询计划、耗时、覆盖率或复现步骤。
   - 没有区分“缺陷”“缺失功能”“技术债”；没有影响描述（财务错报、缺货、收入漏损、审计失败）和根因。
   - 在没有一致性/失效设计的情况下建议缓存财务数据，存在风险。

8. **没有追溯、影响和验收标准。**
   - §6 与 §7 是两套平行主题清单，没有 ID、负责人、依赖、估算、成功指标或“发现→建议”的映射。
   - “更多报表”“查询优化”“统一日志”不是可执行任务。
   - 结论只有四句泛化描述，没有风险排序、go/no-go 或下一步决策。

9. **非功能覆盖薄弱，测试被延后。**
   - 没有数据迁移/回填、备份/恢复/灾备（RPO/RTO）、可观测性（指标/追踪/告警/SLO）、并发/幂等、CI/CD/回滚、合规。
   - 测试被放在 P2，但 P0 会改会计；财务回归/黄金数据集测试应属于 P0 验收，而不是后续阶段。

10. **会计控制只点名、未评估。**
    - 没有借贷平衡强制、控制科目、试算平衡、过账/反过账、冲销 vs 删除、截止性、预提、收入确认、税务过账、舍入、已实现/未实现汇兑、重估、合并等控制。
    - 对 ERP 审计来说，这些才是财务结论的核心依据。

11. **没有流程、依赖和切换计划。**
    - 清单是页面/功能，不是端到端流程（O2C、P2P、R2R）；没有状态机、审批阈值、职责分离、信用额度、三单匹配、退货授权和异常处理。
    - 总账、成本、汇兑被并列，但成本依赖库存/总账，折算依赖总账，结账依赖子账过账；没有依赖图、并行运行、历史余额迁移或切换/回滚方案。

#### Minor

- “60+ 张表”与 §3 实际列出的 60 张不一致。
- 凭证打印有功能描述，但没有 API/页面路由。
- 没有术语表，导致“总账/复式记账/结账/期末结转”前后矛盾。
- §8 的“代码结构清晰、模块划分合理”没有代码度量、分层检查或依赖分析支撑。
- 归档说明引用的两个后续文件在评审时不存在（本次已补齐）。
- Flask 2.3/Vue 3.3 对 2026 年报告偏旧，没有 EOL/CVE 检查，却建议“依赖升级”。
- §2 的功能清单是菜单级，不含状态、角色、校验和业务规则。

### 2.3 遗漏或薄弱的领域

- **多租户**：租户模型、隔离、开通、按租户配置、跨租户测试。
- **安全**：威胁模型、JWT/会话撤销、密钥、注入/XSS/CSRF、限流、MFA、加密、依赖扫描、审计日志不可篡改、PII/PIPL。
- **审计轨迹**：登录/操作日志的完整性、不可篡改、保留期、before/after、字段级变更、财务审计轨迹。
- **数据迁移/备份/灾备**：历史数据导入、对账、备份恢复演练、RPO/RTO、HA/故障切换、归档。
- **可观测性**：指标、追踪、告警、SLO、健康检查；过账失败、单据卡住、队列积压无人监控。
- **并发/幂等**：单号并发生成、重复提交、幂等键、乐观锁、超卖、核销竞争、死锁、隔离级别、Outbox/重试安全。
- **会计正确性**：借贷平衡、控制科目、试算平衡、过账规则、冲销、期间锁定/截止、预提、收入确认、税务、舍入、汇兑重估/折算、合并。
- **存货计价**：移动平均机制、负库存、退货/调拨/盘点、 landed cost、成本调整、重算、COGS 时点。
- **审批流**：现状图、审批矩阵、阈值、委托、升级、职责分离、审计历史。
- **报表**：正确性/对账、参数、钻取、导出、调度、行级安全、同比/环比、多币种折算。
- **性能测量**：数据量、并发、SLA、查询计划、压测；§6.6 的结论没有量化。
- **测试**：测试金字塔、框架、CI 门禁、覆盖率目标、财务黄金数据集、E2E/UAT、迁移测试。
- **部署/运维**：CI/CD、环境、配置/密钥、迁移/回滚、蓝绿、监控、事件响应、容量、离线/License 安装。
- **合规**：中国会计准则、增值税/电子发票、留存、PIPL/数据驻留、无障碍、本地化。
- **业务上下文与流程**：角色/画像、数据量、行业、O2C/P2P/R2R、信用控制、三单匹配、职责分离。
- **零售特有**：POS、门店补货、促销、会员/积分、条码、保质期、电商、退换货；若实际是贸易/分销，应改标题。
- **集成/税务**：银行流水、支付网关、电子发票、电商、物流、条码设备、纳税申报；含税/不含税、舍入没有评估。
- **数据质量/主数据**：重复、校验、单位换算、税码、汇率来源、信用额度、供应商准入。
- **API/前端非功能**：版本、分页/过滤/错误标准、幂等、OpenAPI 覆盖；无障碍、响应式/移动端、浏览器支持、错误边界。

### 2.4 报告评审结论

**可作为 ERP 领域检查表，不能作为可复现审计证据。** 报告的主题方向有价值，但缺少方法、证据、范围定义和可验收的任务分解；财务部分存在直接矛盾；P0 计划不可执行且重复规划。对 `mlf-erp` 应“用报告的问题，不用报告的结论”。

## 3. 对照口径

- **按能力对照**：报告使用 Flask/SQLAlchemy/MySQL、`sys_* / md_* / sd_* / pd_* / inv_* / fin_*` 表名和 `/api/...` 路径；`mlf-erp` 使用 Go/Gin/PostgreSQL、`erp.*` 表名和 `/api/v1/...` 路径。逐字对照会产生大量假差异。
- **状态定义**：
  - **已完成**：有领域模型、迁移、API、前端/测试，且当前主线可用。
  - **部分完成**：主流程可用，但报告指出的能力只覆盖一部分。
  - **未实现**：没有对应领域/表/API，或只有目录骨架。
  - **不适用**：报告的技术栈/产品范围与 `mlf-erp` 不同，不能直接套用。
  - **未验证**：报告有主张，但当前仓库没有基线/度量/测试可证实或证伪。
- **证据来源**：根 `README.md`、`db/migrations/README.md`、`internal/modules/*`、`api/openapi.yaml`、`tests/api/*`、`apps/web/src/views/*`。
- **规模基线（本次统计）**：`erp` schema 50 张表；OpenAPI 65 个 path；11 个后端模块（其中 manufacturing/quality/project/reporting 为骨架）；25 个迁移；31 个 Vue view；11 个 API 集成测试函数；113 个 Go 单元测试函数。

## 5. 审计建议在 mlf-erp 的适用性重排

### 5.1 已完成，不应重做

- 复式记账总账、自动凭证、科目/期间、试算平衡、总账/明细账、资产负债表、利润表。
- 期末关账、损益结转、反关账、年度结转/利润分配。
- 税务发票、价税分离、销项/进项、VAT 汇总。
- 多币种、汇率、已实现汇兑、期末重估、反关账撤销重估。
- 现金流量表（直接法 + 简化间接法）。
- 销售/采购退货、贷项单、贷项抵用、退款、退款凭证。
- 收付款核销与整行反核销、汇兑结算反核销凭证。
- 采购收货→应付、销售发货→应收、发货/收货/收付款自动凭证。

### 5.3 未实现，真实差距

- **审批流与职责分离**：可配置审批流程、阈值、节点、审批人、条件、历史、禁止自批。
- **库存作业**：调拨、盘点/调整、预留、库存预警、可用量。
- **批次/序列号/保质期**：批次追踪、序列号、先进先出/保质期、追溯。
- **字段级权限**：字段读写/脱敏、按角色/组织配置。
- **数据范围管理 API/UI**：当前只能通过用户/组织数据推断，缺少管理界面。
- **报表中心**：销售/采购/库存/账龄/对账/导出/图表。
- **AR/AP 发票行与手工开票**：当前发票仅表头，由发货/收货自动生成；无发票行、手工开票、红字发票。
- **平台适配器与能力控制**：Worker/Outbox/Redis/MinIO/RabbitMQ 仅接口或占位；`runtime-config` 宣称 manufacturing/quality/project/reporting，但模块为空；无 `RequireCapability` 强制。
- **租户开通与管理**：无 tenant CRUD/onboarding；租户靠 seed/config。
- **财务扩展**：账龄、对账单、信用额度、付款/预收款退款、银行对账、固定资产、合并报表。
- **前端基础体验**：`el-form` 规则校验、404 路由、改密/个人资料页、Dashboard 真实指标、金额/日期格式化、i18n、列配置。
- **契约完整性**：OpenAPI 补 system/masterdata 路径、修正 `masterdata` enable 路径、契约测试/生成的 SDK。
- **资金操作幂等**：`Idempotency-Key`、重复提交去重、并发安全。
- **安全加固**：登录限流/锁定、token version、httpOnly Cookie 评估、RLS、密钥管理、依赖扫描、渗透测试。
- **可观测性**：指标、追踪、告警、SLO、过账失败/队列积压监控。
- **备份/灾备/切换**：备份恢复演练、RPO/RTO、历史余额迁移、并行运行、回滚方案。

### 5.4 不适用或低优先级

- 零售 POS、门店补货、促销、会员/积分、条码/电商：只有产品范围转向零售时才做；当前 `mlf-erp` 更接近贸易/分销。
- manufacturing/quality/project：当前是目录骨架，且不在审计的贸易/分销范围内。
- 完整合并报表、多会计准则、完整 BI：长期能力，不应进入近期 P0。
- 重建总账/汇兑/期末结转：已完成，重做会浪费并引入回归风险。
- 把审计报告的 Flask/MySQL 表名、端点、页面直接映射到 `mlf-erp`：不适用。

### 5.5 审计遗漏但应优先

1. **资金操作幂等与重复提交**：退款、收付款、反核销、发货、收货、退货。
2. **审批与职责分离**：金额阈值、禁止自批、审批历史不可篡改。
3. **备份/恢复/灾备**：RPO/RTO、恢复演练、迁移/切换。
4. **可观测性**：过账失败、单据卡住、队列积压、接口错误率和延迟。
5. **多租户 RLS 与安全基线**：应用层过滤 + RLS 双保险、限流、密钥、依赖扫描。
6. **数据迁移/历史余额**：从旧系统迁移时的科目余额、未核销单据、库存成本。
7. **合规**：中国会计准则、增值税/电子发票、PIPL/数据驻留。
8. **性能基线**：没有数据量、并发、SLO 和查询计划，无法判断“N+1/缺索引”是否真实。
9. **平台适配器与能力控制**：Worker/Outbox/Redis/MinIO/RabbitMQ 适配、capability 强制、租户开通。

## 7. 结论

这份报告的价值在于**提出了正确的 ERP 问题类别**，而不是提供了 `mlf-erp` 的可靠现状。它把“财务核算完整性、权限、库存成本、审批流、报表、性能、测试、文档”摆上了桌面，但缺少证据、范围定义和可执行分解，财务部分还自相矛盾。

对 `mlf-erp` 的正确用法是：

- 把报告当**问题假设清单**，逐项用代码/迁移/测试验证。
- **不要重做**已完成的总账、汇兑、期末结转、退货/贷项/退款、反核销。
- 把近期投入放在**资金操作幂等/审批、成本核算收口、库存作业、权限精细化**，再进入报表中心和工程加固。
- 每个阶段继续沿用现有流程：设计 → 计划 → 代码审核 → 接口测试 → 报告 → 用户审阅。

后续路线图见 `docs/superpowers/plans/2026-11-25-audit-follow-up.md`。
